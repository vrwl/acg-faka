# 数据表与口径

22 张表，全部以 `wm_` 开头（实际表名还有站点自己的表前缀，通常是 `acg_wm_*`）。建表完全由 `Core/Schema.php` 幂等完成，不用 `install.sql`：启用 / 升级时对照 `VERSION` 常量自动补列补索引，跑一百次和跑一次结果一样。

## 表一览

### 明细与会话

| 表 | 内容 | 默认保留 |
|---|---|---|
| `wm_access` | 原始访问日志，一行一个请求 | 30 天 |
| `wm_session` | 会话（一次访问），含入口页、来源、时长、页数、是否跳出 | 30 天 |
| `wm_visitor` | 访客档案，跨会话累计 | 180 天 |
| `wm_online` | 在线快照，`last_at` 决定谁算在线 | 在线窗口 × 3 |
| `wm_seen` | 去重表，UV / 独立 IP 的**唯一**计数依据 | 分桶 3 / 30 / 7 天 |

`wm_access` 是唯一会被采样的表：设置里的「明细采样率」只作用于它，其它所有表和聚合数据始终精确。

### 时序与聚合

| 表 | 粒度 | 默认保留 |
|---|---|---|
| `wm_stat_min` | 每分钟 | 3 天 |
| `wm_stat_hour` | 每小时 | 180 天 |
| `wm_stat_day` | 每天 | 永久 |
| `wm_agg` | 每天 × 每个维度 × 每个取值 | 400 天 |

`wm_agg` 是面板所有 TOP-N 排行的支点，主键 `(day, dim, key_id)`，配 `(day, dim, pv)` 索引。`dim` 的取值：

| 值 | 维度 | 值 | 维度 |
|---|---|---|---|
| 1 | 页面 | 11 | 地区 |
| 2 | 来源网址 | 12 | 时段 |
| 3 | 来源域名 | 13 | 语言 |
| 4 | 搜索引擎 | 14 | utm_source |
| 5 | 着陆页 | 15 | utm_medium |
| 6 | 退出页 | 16 | utm_campaign |
| 7 | 浏览器 | 17 | 搜索词 |
| 8 | 操作系统 | 18 | 状态码 |
| 9 | 设备 | 19 | 来源类型 |
| 10 | 蜘蛛 | | |

### 字典

| 表 | 内容 |
|---|---|
| `wm_page` | 路径 → 数字 ID |
| `wm_referer` | 来源网址 → 数字 ID |
| `wm_ua` | User-Agent → 数字 ID |
| `wm_dict` | 通用字典（域名、搜索词、UTM 值…） |
| `wm_region` | 地区码 → 中文名 |

把宽字段搬出明细表，`wm_access` 每行只存几个整数 ID。同一个 URL 出现一百万次也只在字典里占一行。

### 安全

| 表 | 内容 | 默认保留 |
|---|---|---|
| `wm_rule` | 人工规则：IP 黑/白、地区黑/白、UA 黑、路径豁免 | 永久 |
| `wm_ban` | 自动封禁 | 按各自 TTL |
| `wm_attack` | 攻击取证 | 14 天 |
| `wm_ip` | IP 画像：累计请求、累计攻击、首末出现 | 随访客档案 |

`wm_attack` 故意留得短 —— 它存的是攻击者提交的原始载荷片段，里面可能夹着别人误提交的真实数据。取证已经做过脱敏（`password|token|secret|sign|card|cvv` 类字段值打码、Cookie 整体 `***`、只存命中片段前后各 64 字节），但仍然不该长期留着。

### 蜘蛛与状态

| 表 | 内容 |
|---|---|
| `wm_spider` | 蜘蛛签名，55 条内置 + 自定义 |
| `wm_spider_ip` | 反查结果缓存（PTR + 正向确认），7～30 天 |
| `wm_kv` | 带 TTL 的键值状态 |
| `wm_ingest` | 入库幂等标记，2 天 |

## 幂等契约（改代码前必读）

`wm_agg` 有两条写路径，各改各的列，**互不干扰**：

| 列 | 谁写 | 方式 |
|---|---|---|
| `pv` | 入库任务 | **增量累加** |
| `visits` `uv` `bounce` | 汇总任务 | 从 `wm_session` **全量重算后覆盖** |

汇总任务用的是 `ON DUPLICATE KEY UPDATE col = VALUES(col)`（覆盖，不是累加），所以对同一天跑一次和跑一百次结果完全相同。面板上的「重建当前区间的汇总」按钮可以随便点，不会把数据算重。

入库任务的幂等靠 `wm_ingest` 的封存文件名标记：同一个 spool 文件重放会被直接跳过。

**如果你要改这部分代码**：别把汇总列改成累加，也别让入库任务碰 `visits/uv/bounce`。这两条约束一破，重跑汇总就会翻倍。

## MySQL 5.7 兼容约束

代码里有几处看起来"绕"的写法，都是为了兼容 5.7：

- **没有 `upsert()`**（Illuminate 7.30 才有 8.x 的那个），批量写全部走自己拼的 `ON DUPLICATE KEY UPDATE ... VALUES()`。
- **不用窗口函数和 CTE**，排行榜靠 `wm_agg` 的索引直接排序。
- **不用 `Blueprint::binary()`**：Illuminate 的 MySQL 语法把它编译成 `blob`，而 `blob` 建不了索引。所有 IP 和哈希列都是 `char(N) charset ascii collate ascii_bin` 存 hex —— 定长、可索引、比较快。

## 会话首属性的确定方式

一次会话的「入口页」「来源」「搜索引擎」「是否新访客」必须取**这次会话第一个请求**的值。但 spool 是 8 个分片并行写的，同一秒内的请求跨分片时，仅靠时间戳排不出先后。

所以 `wm_session` 有一列 `entry_rank`：标记了「新会话」的那条记录 rank 为 0，其余取时间戳。写入时用

```sql
IF(VALUES(`entry_rank`) < `entry_rank`, VALUES(`entry_page`), `entry_page`)
```

保证只有更早的那条能覆盖首属性。**赋值顺序有意义** —— MySQL 从左到右求值，`entry_rank` 必须放在所有依赖它的列**后面**，否则它先被更新，后面的比较全部失效。改这段 SQL 时留意列顺序。

## 分区

设置里可以打开「明细表按天分区」，`wm_access` 会按 `day` 列做 RANGE 分区。好处是清理 30 天前的数据从全表 `DELETE` 变成 `DROP PARTITION`：秒级完成、不锁表、不产生 binlog 洪水。

日均超过 100 万行的站点强烈建议开。开启是在线操作，但会重建一次表，建议在低峰期点。

## 运行时目录

```
runtime/plugin/WebsiteMonitor/
├── state.php          模式 / 守护心跳 / 采样率 / 忽略路由（30 秒级变动）
├── rules.php          规则与名单的编译产物（天级变动）
├── spiders.php        蜘蛛签名编译产物
├── DISABLED           这个文件一存在，全部防护立即停止
├── spool/s0..s7.log   采集分片，追加写
├── spool/seal/        已封存待入库
├── ban/               一个 IP 一个文件，热路径只要一次 is_file
├── cc/                限频计数器（无 Redis 时）
├── geo/               IP 库与元数据
└── spider/            反查中间态
```

**编译态故意拆成三个文件**：心跳每 30 秒刷新一次 `state.php`，如果和规则合成一个文件，每次心跳都会让 opcache 失效并重新编译几百 KB 的规则数组。

**自动封禁不进编译快照**，走 `ban/` 目录一 IP 一文件。封禁是秒级写入的，每封一个 IP 就重写一次快照，等于在被攻击时自己 DoS 自己。人工规则才进 `rules.php`。
